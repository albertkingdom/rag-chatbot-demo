## Context

語意快取由 src/cache_service.py 的 PromptCacheService 實作。每筆快取是一個字串 key（前綴 prompt_cache: 加 embedding 雜湊前 16 碼），值為 JSON（問題、答案、來源、embedding、時間戳、hit_count），以 setex 寫入並帶 24 小時 TTL。所有 key 另外登記在一個 Redis Set（prompt_cache:index）。查詢時以 smembers 取出整個 Set，轉成 list 後只取前 CACHE_MAX_SEARCH_RESULTS（5）筆，用 pipeline 逐筆 GET，再以 numpy 算 cosine 相似度，嚴格大於門檻 0.95 才算命中。

限制與背景：

- 每筆值內含 1536 維 embedding 的 JSON 浮點陣列。審查時以合成資料模擬，每筆約 35KB，50 筆約 1.76MB，僅 json.loads 就約 12 毫秒（Python 3.9 的本機模擬，不含網路傳輸與 numpy 轉換）。
- 聊天服務層在 async 函式裡同步呼叫快取服務與 Redis，查詢期間會阻塞同一個事件迴圈；Cloud Run 同一 instance 預設可並行處理多個請求，且 Terraform 設定最大 instance 數為 1。
- Redis client 為 redis-py 8.0.1（見 requirements.txt）；連線沒有設定 decode_responses，所以成員與值以 bytes 回傳。其預設通訊協定為 RESP3，但回應會轉回舊格式：審查讀 redis-py 原始碼確認，不帶分數的 ZRANGE 與 ZREVRANGE 回傳 bytes 清單、SMEMBERS 回傳 set，pipeline 預設即為 MULTI 與 EXEC；對真實 Redis 的行為仍未實測。
- 正式環境 Redis 的提供者與限制（單次回應大小、指令數計費）無法從 repo 判斷；較早的 gcp-deployment 變更曾提到使用託管的免費層 Redis，是否仍適用未驗證。本機為 redis:7-alpine。
- docker-compose.yml 與 Terraform 目前只傳遞列舉出的環境變數，新增的設定不會自動傳進容器。
- 手冊同步流程不會清除語意快取，且既有的清除方法沒有任何呼叫者。

## Goals / Non-Goals

**Goals:**

- 快取內任何一筆未過期的條目都有機會被比對，結果與行程、插入順序無關。
- 索引有明確上限與淘汰規則，不會無限成長，且並行寫入不會讓索引少於上限。
- 過期與損壞條目在查詢時被處理，不依賴「剛好被抽到」，也不會讓單筆問題拖垮整個查詢。
- 對外介面（方法簽章與回傳內容）不變，聊天服務層不需修改。

**Non-Goals:**

- 不改相似度門檻、TTL、hit_count 規則與快取值的 JSON 結構。
- 不改 embedding 儲存格式，不使用 Redis 向量搜尋，不引入行程內向量快取。
- 不修改聊天服務層，不處理同步呼叫阻塞事件迴圈，不處理手冊同步後清快取，不處理低分答案是否寫入快取。
- 不接線 docker-compose.yml 與 Terraform 的環境變數。

## Decisions

### 索引改為以寫入時間排序的 Sorted Set 並使用新 key 名稱

新索引 key 為 prompt_cache:index:zset，member 是資料 key，score 是寫入時的浮點秒數，由建構子的選用時鐘參數提供（預設為系統時間，測試注入嚴格遞增的時鐘）。同分時 Redis 依 member 字典序排列，而 member 是雜湊，與寫入順序無關；使用浮點秒數可使同分極少發生，測試則以注入時鐘避免同分。同一個問題重複寫入時，ZADD 對既有 member 只會更新 score，不會增加筆數，自然維持「同 key 不重複」。

替代方案：

- 沿用 Set 並改為完整掃描：沒有上限、沒有「最近」的概念，傳輸量不可控。
- List 加 LTRIM：重複寫入同一 key 時要額外 LREM 去重，且沒有 score 可用。
- Redis 向量搜尋：正式環境是否支援未驗證。
- 行程內快取已解析的向量：因為資料 key 是 embedding 內容的雜湊、內容不會改變，所以技術上可行且沒有一致性問題；本次不做，是為了控制範圍與測試複雜度，若量測顯示傳輸或解析成本過高再做（後續項目）。

必須使用新 key 名稱：若沿用 prompt_cache:index，既有環境裡該 key 是 Set，對它執行 ZADD 會得到 WRONGTYPE 錯誤，快取會被 try/except 吞掉而靜默失效，直到舊 key 被手動刪除。

### 查詢涵蓋整個有上限的索引且上限預設為 50

查詢取新索引中最近的 CACHE_MAX_ENTRIES 筆（由新到舊），索引本身也以同一個上限封頂，所以「比對範圍」等於「整個索引」。設定 CACHE_MAX_SEARCH_RESULTS 以 CACHE_MAX_ENTRIES 取代，只保留一個旋鈕，避免兩個設定語意互相矛盾，預設 50。

設定值必須是不小於 1 的整數：0 會讓「取最近 0 筆」被寫成取全部、並讓淘汰清空整個索引；負數同樣出錯；非整數會在載入設定時丟出例外而讓應用程式無法啟動。因此未設定時採用預設 50（不警告，正式環境不傳這個變數）；設定了但不是整數或小於 1 的值採用預設 50 並記錄警告。解析邏輯抽成可直接呼叫的函式，測試直接驗證它的結果與警告，而不是靠重新匯入模組；查詢與寫入在呼叫時才讀取設定值（不在定義時綁定），並接受建構子的選用上限參數供測試注入，調降上限的情境也由此測試。可由環境變數覆寫，但 docker-compose.yml 與 Terraform 目前不會傳遞它，正式環境調整需另行接線，這不在本變更範圍。

取捨依據：知識庫約 126 筆 Q&A（依架構文件，內容未驗證）、快取 TTL 24 小時；50 筆是否足以涵蓋近期的相異問題尚無資料支持（推測），上線後可從 MongoDB 的 rag 紀錄統計每日相異問題數再調整。每個 rag 請求都要付一次全量讀取與解析的成本，約 1.8MB 與數十毫秒的解析（見背景的模擬數字），且同步執行會阻塞事件迴圈。因此預設取較保守的 50，實作時以量測腳本量測包含 numpy 轉換的解析與比對時間，結果補記在本決策下方。硬門檻：50 筆的單次耗時（解析、numpy 轉換與比對合計）若超過 50 毫秒，預設上限必須調降到耗時不超過 50 毫秒的值並在此說明，否則維持 50。

量測結果（任務 7.1，scripts/benchmark_cache_lookup.py）：合成資料為 1536 維完整精度浮點數、約 400 字答案與 3 筆來源，每筆值約 36KB；環境為 Apple M3 Max 上 Docker Desktop 的 Linux 虛擬機（8 核心），Python 3.13.16、numpy 2.5.0、aarch64；每項取 50 次的中位數，不含 Redis 往返與網路傳輸（`--repeat 50`；另一次重跑的差異在 0.3 毫秒內）。

| 筆數 | 讀回量 | json.loads | numpy 轉換 | cosine 比對 | 三者合計 | 完整 get_cached_response |
| ---- | ------ | ---------- | ---------- | ----------- | -------- | ------------------------ |
| 50   | 1.79MB | 14.7 ms    | 1.2 ms     | 0.10 ms     | 16.1 ms  | 17.2 ms                  |
| 100  | 3.57MB | 29.9 ms    | 2.6 ms     | 0.20 ms     | 32.8 ms  | 34.8 ms                  |

結論：50 筆的單次耗時約 17 毫秒，低於 50 毫秒的硬門檻，所以預設維持 50，不調降。耗時約九成在 JSON 解析，numpy 轉換與比對合計不到 2 毫秒，且隨筆數線性成長（100 筆約 35 毫秒）；若日後需要壓低成本，行程內快取已解析的向量才會有效。限制：這是開發機的數字，Cloud Run 的 CPU 配額可能較慢（目前約有 3 倍餘裕），Redis 往返與傳輸 1.8MB 的時間也未量測。

### 以單一 MGET 讀回條目並逐筆容錯

索引為空時直接回傳未命中，不發出 MGET（redis-py 8.0.1 對空清單的 MGET 會直接回傳空清單而不報錯，這樣做是為了省一次往返）。否則對索引成員一次 MGET，而不是 N 次 GET。逐筆處理規則：

- 值為 None：資料 key 已過期，成員移出索引。
- 值不是合法 JSON，或解析結果不是物件：略過並移出索引。
- 缺少 embedding、embedding 不是數字陣列、或計算相似度時出錯（例如維度不符）：只略過該筆。
- answer 不是非空字串，或 sources 缺漏或不是字串清單：略過並移出索引。這類條目若被命中，聊天服務層無法送出答案或來源，且同一問題在 24 小時內都會重複失敗，所以必須在此排除；缺 sources 不採用空清單 fallback，與 add-answer-sources 規格「缺欄位不得 fallback」一致。

因為現在每次查詢都掃過整個索引，單一損壞條目若會丟出例外，就會讓每次查詢都失敗，所以逐筆容錯是必要的，不是額外功能。移出索引時只在清單非空時才發出 ZREM。

替代方案：pipeline 逐筆 GET（同樣只有一次往返，但指令數隨 N 增加，若 Redis 提供者按指令計費則成本放大）。

### 寫入以交易淘汰最舊並刪除其資料 key

寫入流程：先讀取既有值以保留 hit_count（既有值無法解析時 hit_count 視為 0 並照常寫入，避免單一損壞值讓該問題在 TTL 內無法再寫入快取），再 setex 寫資料 key；接著在同一個交易中依序執行 ZADD 登記、取出「最新 N 筆以外」的成員（範圍為 0 到 -(N+1)，例如 N=50 時為 0 到 -51；筆數不足 N 時取出空清單）、以相同範圍 ZREMRANGEBYRANK 從索引移除；交易完成後，若取出的成員非空，再刪除這些成員的資料 key。以範圍運算移除「最新 N 筆以外」可以省去 ZCARD 與位移計算，並使並行寫入下的索引筆數收斂到 N（審查以窮舉兩個寫入者的所有交錯確認，這一點與是否使用交易無關）。使用交易的理由是讓「取出的成員清單」與「實際從索引移除的成員」一致，之後刪除的資料 key 才恰好等於這次移除的成員，不會誤刪其他寫入者剛登記的條目，也不會留下孤兒資料。

淘汰順序是先進先出（以寫入時間）；命中不會更新 score，讓 score 與 TTL 起點一致；同一問題重新寫入時 score 會更新。

替代方案：只修剪索引、讓資料 key 靠 TTL 自然過期。不採用，因為淘汰後的資料 key 會成為孤兒最長存活 24 小時，寫入量大時佔用的記憶體約為「24 小時內的寫入數 × 每筆大小」，不可控。命中時更新 score（LRU）列為後續項目。

交易之外的刪除若與同一 key 的重新寫入交錯，最壞結果是新條目的資料 key 被刪、索引仍登記該 key，下一次查詢讀到 None 時會被清理；不會造成錯誤命中。

### 舊 Set 索引不遷移且清除快取時一併刪除

部署後新程式碼只讀寫新索引，舊 Set 中登記的資料 key 無法被查詢到，並在 24 小時內自然過期，因此快取在部署後等同冷啟動。清除快取時額外讀取舊 Set，刪除其登記的資料 key 與舊 Set 本身；回傳的筆數是新舊索引合計、去除重複後的資料 key 數量。舊 Set 本身只有幾個 key 字串的大小，可保留到下次清除，或由維運者在確認不需回復後手動刪除。

### PromptCacheService 對外介面維持不變

取得快取與寫入快取的方法簽章、回傳 dict 的鍵（問題、答案、來源、相似度、hit_count）都不變；建構子只新增兩個有預設值的選用參數（時鐘與上限），既有呼叫端不需修改。聊天服務層與其測試不需修改。

## Implementation Contract

**Behavior**

- 查詢：給定問題 embedding 與門檻，系統比對新索引內全部條目（至多 CACHE_MAX_ENTRIES 筆，由新到舊），回傳相似度嚴格大於門檻且最高的一筆；命中時 hit_count 加 1 的行為不變；沒有命中回傳 None；索引為空時不發出 MGET。
- 寫入：資料 key 以 TTL 寫入；以目前時間為 score 登記到新索引；索引超過上限時淘汰最舊的成員並刪除其資料 key；同一 embedding 重複寫入時保留既有 hit_count，索引筆數不增加。上限被調降後，下一次寫入會把索引縮到新上限；查詢只讀最新的上限筆數。
- 設定：CACHE_MAX_ENTRIES 為不小於 1 的整數；未設定時為 50 且不警告，設定了但不是整數或小於 1 時為 50 並記錄警告。
- 清除與統計：清除快取刪除新索引、其所有資料 key，以及舊 Set 索引與其登記的資料 key，回傳去重後的資料 key 數；統計改讀新索引。

**Interface / data shape**

- 資料 key：沿用 prompt_cache: 加 16 碼十六進位雜湊，值的 JSON 結構不變；answer 必須是非空字串、sources 必須是字串清單，否則視為無效條目。
- 新索引 key：prompt_cache:index:zset，型別為 Sorted Set，member 為資料 key，score 為寫入時的浮點秒數。
- 舊索引 key：prompt_cache:index，型別為 Set；查詢與寫入不讀寫它，只有清除快取時移除。
- 設定：CACHE_MAX_ENTRIES；CACHE_MAX_SEARCH_RESULTS 移除。
- 建構子：PromptCacheService(redis_connection, clock=選用，預設系統時間, max_entries=選用，預設在呼叫時讀取設定值)。

**Failure modes**

- 查詢過程中任何 Redis 例外：回傳 None 並印出錯誤（既有行為不變）。
- 寫入過程中任何 Redis 例外：回傳 False（既有行為不變）。
- 單筆條目損壞：依「逐筆容錯」規則略過，不影響其他條目。
- 舊 Set 索引存在：不產生 WRONGTYPE 錯誤，不影響新索引運作。

**Acceptance criteria**

- tests/test_cache_service.py 以記憶體內的假 Redis 驗證，假 Redis 須貼近真實行為：回傳 bytes、同分依成員字典序、支援負索引、對空參數的 ZREM 與 DEL 報錯、MGET 空清單回傳空清單、交易依序執行並可檢查交易內容、對 Set 執行 ZADD 時報 WRONGTYPE。涵蓋：20 筆中最舊一筆可命中；索引為空不發 MGET；寫入超過上限後筆數等於上限且被淘汰者的資料 key 已刪除；寫入的登記、取出超額、移除超額三個指令在同一個交易內依序排隊，且之後刪除的資料 key 恰好等於移除的成員；上限被調降後下一次寫入縮到新上限；一次查詢移除所有過期成員；非 JSON、非物件、缺 embedding、維度不符、answer 或 sources 缺漏或型別無效的條目不阻斷其他條目；既有值損壞時寫入仍成功且 hit_count 為 0；舊 Set 同時存在時讀寫正常；hit_count 保留；清除快取同時清掉新舊索引並回傳去重筆數；CACHE_MAX_ENTRIES 的未設定（不警告）、非整數、0、負數（皆警告）、有效值。
- 既有測試改寫為新索引 API 後全部通過，且改寫後的案例確實走到相似度比對（現有的低相似度與缺 embedding 兩個測試因為沒有設定 pipeline 而根本沒比對）；其他測試檔不需修改即可通過。
- 量測腳本已提交，結果（含 numpy 轉換）記錄在本文件。
- architecture.md 的快取章節、關鍵參數表與已知問題表已同步更新，已知問題表改為列出目前仍存在的問題（同步呼叫阻塞事件迴圈、手冊同步不清快取）。

**Scope boundaries**

- 範圍內：src/cache_service.py、src/config.py、tests/test_cache_service.py、scripts/benchmark_cache_lookup.py、architecture.md、.env.example（補上 CACHE_MAX_ENTRIES 說明，以 BM25_RELOAD_INTERVAL_SECONDS 為先例）。
- 範圍外：聊天服務層、docker-compose.yml 與 Terraform 的環境變數、embedding 儲存格式、相似度門檻與 TTL、向量搜尋、行程內向量快取、手冊同步後清快取、低分答案的快取寫入規則。

## Risks / Trade-offs

- [每個 rag 請求的快取查詢最多讀回約 1.8MB 並同步解析，期間阻塞事件迴圈] → 預設值保守；量測腳本量測含 numpy 的成本；以 asyncio.to_thread 包裝或行程內向量快取列為後續項目。
- [查詢範圍擴大後，手冊同步前寫入的舊答案與低分答案會在 24 小時內被穩定命中，而同步流程不清快取] → 建議在 handle-low-confidence-retrieval 之後合併或同版部署；手冊同步後清快取列為後續項目，並記在已知問題表。
- [正式環境 Redis 對單次回應大小或指令數的限制未驗證，且上限無法由正式環境的環境變數調整] → 部署前由維運者確認；必要時調整預設值並重新部署，或另案接線環境變數。
- [對真實 Redis 的行為未實測；審查已讀 redis-py 8.0.1 原始碼確認回應轉為舊格式] → 假 Redis 以 bytes 為準；任務中安排一次本機 Redis 手動驗證。
- [部署後快取冷啟動] → 可接受；舊資料 24 小時內自然過期，新條目隨查詢重建。
- [查詢端移出過期或損壞成員的 ZREM，可能與同一 key 剛完成的重新寫入交錯，使新條目暫時不在索引] → 該條目的資料 key 仍存在，下次寫入同一問題會重新登記，影響只是一次未命中。
- [先進先出可能淘汰仍熱門的條目] → 被淘汰後下一次未命中會重新寫入；LRU 列為後續項目。
- [回復到舊版程式碼時，新索引成為無人讀取的孤兒] → 資料 key 24 小時內過期，新索引可手動刪除。

## Migration Plan

1. 合併後部署新版本；不需要手動遷移，也不需要停機。
2. 部署後快取為冷啟動，舊的資料 key 在 24 小時內過期；舊 Set 索引可保留，或在確認不需回復後由維運者手動刪除。
3. 回復：回到舊版程式碼即可，舊版讀的是舊 Set；新索引的 Sorted Set 可手動刪除。
4. 與 handle-low-confidence-retrieval 的順序：先合併它，或兩者同版部署；本變更使快取冷啟動，可順帶清掉既有的低品質答案。
