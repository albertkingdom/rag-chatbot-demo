## Problem

同一個對話中重複問「忘記密碼怎麼辦？」，第二次沒有命中語意快取，仍然走完整個 rag 流程（2026-11-18 本機測試，session `DEy0YY`：第一次檢索 top-1 分數 1.0；第二次 0.454、`response_source` 為 rag）。除了快取失效，檢索品質也變差。

## Root Cause

只要有對話歷史，路由器就把每個問題送給 LLM 改寫成「獨立問題」，再用改寫結果做 embedding、查語意快取和檢索。判斷「要不要改」完全交給模型的自由輸出；提示詞雖然要求「問題本身完整時原樣回傳」，模型仍會順手補內容。以當時的對話歷史重現（2026-11-19）：「忘記密碼怎麼辦？」被改寫成「忘記CarbonM的密碼怎麼辦？」；沒有歷史時原樣回傳。改寫後的文字與快取中的問題相似度低於門檻，與知識庫的問題文字也不再相同。

規則層已決定路由的問題走 `_rewrite_only`（純文字輸出）；規則層判斷不出的問題走 `_llm_route`（結構化輸出，路由與改寫一起決定）。兩條路徑都有同樣的問題。

## Proposed Solution

讓模型先以結構化輸出判斷「這個問題是否需要對話歷史才看得懂（追問）」，只有判斷為追問時才採用改寫結果；不是追問時，由程式直接使用使用者的原話，不採用模型輸出的文字。沒有對話歷史時維持現狀：不呼叫 LLM 改寫，使用原話。改寫結果為空或 LLM 呼叫失敗時，使用原話。

兩條路徑都套用：`_rewrite_only` 改用結構化輸出（判斷結果＋改寫文字）；`_llm_route` 的結構化輸出加上同樣的判斷欄位，並在提示詞中說明「完整的問題不是追問，即使補上背景能更具體，也不要補」。

## Non-Goals

- 不減少 LLM 呼叫次數：有歷史時仍會呼叫一次 LLM 判斷是否為追問。以規則判斷追問可省下這次呼叫，但容易漏判追問、讓檢索出錯，另議。
- 不改語意快取的查詢方式（例如再用原話查一次）。真正的追問單看原話意思不完整，用原話查快取可能命中意思不同的答案。
- 不改快取相似度門檻或快取資料結構。
- 不處理同次測試發現的「手冊有寫的問題被判為低信心」，另開 change。

## Success Criteria

- 有對話歷史、問題本身完整時（模型判斷不是追問），路由結果的改寫問題與原話完全相同，即使模型同時輸出了加工過的文字。
- 判斷為追問時，採用模型的改寫結果；改寫為空或呼叫失敗時使用原話。
- 沒有對話歷史時不呼叫 LLM 改寫，路由結果為原話。
- 以 2026-11-18 的對話歷史實測，「忘記密碼怎麼辦？」的改寫問題與原話相同；真正的追問仍被改寫。
- 範例手冊的路由關卡（`scripts/eval_sample_manual.py`）仍全部通過。
- `python -m pytest tests -q` 全部通過，新增的測試在修正前因此問題失敗。
