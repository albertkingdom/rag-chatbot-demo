## Context

rag 路徑的檢索品質處理在 src/chat_service.py 的 chat_event_stream：先以 get_retrieval_chain 檢索並重排，用 src/retrieval_grader.py 的 grade_documents 以 top-1 重排分數判斷是否達到 GRADE_SCORE_THRESHOLD（預設 0.3，可由環境變數覆寫）；未達標且重試次數未滿 RETRIEVAL_MAX_RETRIES（預設 1）時，以 rewrite_for_retry 讓 LLM 改寫查詢並再檢索，新結果直接覆蓋舊結果。目前的迴圈在改寫之前就把重試計數加 1。迴圈結束後不論是否達標，都用手上的 context 與 sources 生成答案；答案完整累積後才經輸出防護，再寫入語意快取、對話歷史與 MongoDB，最後以固定大小分段送出並附上來源事件。

生成 prompt 在 src/rag_pipeline.py 的 _QA_PROMPT，其 system 訊息允許在 context 不相關或為空時改用一般知識回答。這個取捨已記載於 architecture.md，本變更保留它。

相關事實：

- grade_documents 只回傳布林值，沒有公開分數；重排結果的 rerank_scores 是依 rank 排序的 dict 清單，score 欄位為字串。
- 對話紀錄寫入 MongoDB 時已支援 metadata 欄位，聊天服務層目前只在防護攔截的情況帶 metadata。
- 生成鏈有三個呼叫端：聊天服務層的直接回答路徑、rag 路徑，以及 tests/evaluate_rag.py；三者傳入的輸入鍵相同（context、question、history、today）。
- 專案鎖定的 langchain-core 在合併 prompt 的預設變數與呼叫端傳入的變數時，呼叫端的值優先（已由審查閱讀原始碼確認）。
- 目前聊天服務層測試的 fixture 把 grade_documents 固定為回傳 True，且 rerank_scores 只是整數清單，沒有 rank 與 score 欄位。
- 既有 web-frontend 規格要求「有來源時才送出來源事件」，沒有來源時不送。

## Goals / Non-Goals

**Goals:**

- 低信心時使用者一定看得到「知識庫查無直接相關資料」的標示，且不會看到不相關的來源。
- 低信心答案不進入語意快取。
- 重試不會讓結果變差，也不做白費的重試。
- 保留可供事後統計與調整門檻的紀錄。

**Non-Goals:**

- 不改門檻、重試上限預設值、評分方式；不新增 LLM 評分。
- 不改為直接拒答；不新增串流事件或前端顯示。
- 不處理語意快取的查詢範圍問題；不調整評估腳本與題庫。

## Decisions

### 重試保留 top-1 分數較高的檢索結果並與所有已試過的查詢比對

聊天服務層維護「目前最佳」的檢索結果與「每次實際檢索的 top-1 分數」清單：第一次檢索的結果是初始最佳；每次實際執行的重試之後，只有新結果的 top-1 分數嚴格大於最佳時才取代，分數相同保留較早的結果。無檢索結果（重排清單為空）視為最低分，紀錄時為 null。評分是否通過，針對最終保留的結果判斷。

改寫重試查詢時，提供給改寫函式的「不佳結果」是最近一次嘗試的文件。

替代方案：永遠採用重試結果（現況，會變差）；取兩次結果的聯集（context 變長且混入不相關內容，並使來源與分數語意不一致）。

### 改寫查詢與任何已試過的查詢相同時停止重試

改寫函式在 LLM 出錯時回傳原查詢，也可能回傳空字串或僅差空白的字串。比較時先去除前後空白；結果為空，或與任何已試過的查詢（含原查詢與先前的重試查詢）相同，就結束重試迴圈，不再檢索。重試次數只計算實際執行的檢索，因此被略過時不增加。當 RETRIEVAL_MAX_RETRIES 大於 1，迴圈在某次嘗試通過評分、達到上限，或遇到重複查詢時結束。省下的成本是一次 embedding、向量檢索與重排。略過發生在改寫之後，所以改寫用的那一次 LLM 呼叫並不省。改寫時傳入的查詢是上一次嘗試所用的查詢，傳入的「不佳結果」是最近一次嘗試的文件。

### 低信心以最終結果的評分判定並集中在 grade_documents

低信心的定義：對最終保留的結果執行 grade_documents 得到「未通過」，亦即 top-1 分數低於門檻，或沒有任何檢索結果；分數等於門檻為通過。src/retrieval_grader.py 新增取得 top-1 分數的函式，grade_documents 內部改為使用它，使門檻規則只有一處。這個函式依 rank 最小者取分，空清單回傳 None，不把空結果當成 0.0。

測試必須固定門檻值（以測試設定覆寫模組內的門檻），因為門檻可由環境變數調整。

### 低信心答案由伺服器固定加註一句並以提示詞禁止杜撰

低信心時，聊天服務層在生成完成後、輸出防護之前，把固定說明 LOW_CONFIDENCE_PREFIX 與一個空行加在答案開頭；之後輸出防護、對話歷史、MongoDB 紀錄與串流事件看到的都是同一份最終答案，因此標示不依賴模型是否遵守。固定說明常數定義在 src/rag_pipeline.py，且必須不觸發既有輸入輸出防護規則（由測試確認，包含 injection 與 PII 兩類）。

生成 prompt 新增選用變數 confidence_note，放在 system 訊息最後，prompt 上設定預設值為空字串，使不提供該變數的呼叫端不需修改。低信心時傳入 LOW_CONFIDENCE_NOTE，只要求模型：檢索到的資料與問題相關性低；只有資料中明確寫出能回答問題的內容才可引用；關於 CarbonM 產品本身（功能、版本、價格、是否支援某項目等）而資料沒寫的問題，要說明無法確認、不推測也不斷言有或沒有；只有一般常識性的問題才以一般知識簡短回答；不得杜撰 CarbonM 系統的具體操作步驟、畫面或選單名稱；不需要重複說明知識庫查無資料（系統會自行加註）。第二點是在真實環境驗證（2026-10-14）後加入的：原本只寫「否則以一般知識簡答」時，「CarbonM 的手機 App 在哪裡下載？」重複 6 次中有 2 次斷言「目前沒有提供手機 App」，加入此限制後 6 次為 0 次（樣本很小，僅作方向性證據）。說明文字避免使用會觸發既有輸出防護規則的詞（例如與系統提示有關的詞），以降低模型照抄時被誤擋的機率。

低信心時仍把檢索到的 context 交給模型，不清空：門檻 0.3 尚未用資料驗證，分數略低的結果可能仍有參考價值；由模型依說明判斷。說明限定「只有資料明確寫出答案時才可引用」，因此與 system 訊息原有的「使用提供的 context」不衝突。

替代方案：只在 prompt 要求模型自行說明（不需額外程式，但無法保證遵守，也無法自動驗證）；低信心時固定回覆「查無資料」不呼叫 LLM（最安全、最便宜、可確定性測試，但會失去目前明載的一般問答能力，例如被關鍵字誤路由的「忘記 Gmail 密碼」）；清空 context 再生成（會丟棄可能仍有用的資訊）。後兩者列為待決問題。

被關鍵字誤路由的一般問題在低信心時也會被加上固定說明，這是已接受的取捨：標示是誠實的，且回答仍然提供。

### 低信心答案不送來源事件且不寫入語意快取

低信心時，聊天服務層把來源清單視為空，讓既有的送出邏輯因來源為空而不送出來源事件，與 web-frontend 規格「有來源時才送出」相符；快取寫入以「非低信心」為條件。對話歷史與 MongoDB 紀錄照常寫入，因為使用者看得到這一輪回覆，後續追問需要它。回應的 responseSource 維持 rag，避免改動事件格式與前端驗證。

### 檢索信心記錄到對話紀錄的 metadata

rag 路徑寫入對話紀錄（成功與輸出防護攔截兩種情況）時，metadata 加入 retrieval 物件，欄位為：

- top1_score：保留結果的 top-1 分數（浮點數，無檢索結果為 null）。
- attempt_scores：每次實際執行的檢索的 top-1 分數，依執行順序，第一個是原查詢，無檢索結果的項目為 null。
- retry_count：實際多做的檢索次數，等於 attempt_scores 的長度減 1。
- kept_attempt：保留的是第幾次檢索（整數，0 為原查詢，1 為第一次重試，依此類推）。
- low_confidence：是否低信心（布林）。
- threshold：評分當下使用的門檻（浮點數；門檻可由環境變數調整，記錄它才能事後解讀分數）。
- retry_skipped：重試是否因改寫查詢為空或重複而提早結束（布林）；沒有進行重試（例如上限為 0 或第一次就通過）時為 false。

通過與否可由 low_confidence 推得，因此不另設 grade_passed 欄位。防護攔截時保留原有的 pii_type 與 injection_pattern 欄位。快取命中與 direct 路徑沒有檢索，不加此欄位。

## Implementation Contract

**Behavior**

- 重試：只有 top-1 分數嚴格較高的重試結果會取代保留的結果；改寫查詢為空或與任何已試過的查詢相同時不發生檢索並結束重試。
- 低信心回應：答案開頭為 LOW_CONFIDENCE_PREFIX 加一個空行；生成輸入的 confidence_note 為非空的 LOW_CONFIDENCE_NOTE；事件序列不含 sources 事件；語意快取沒有新條目；對話歷史新增這一輪（內容含固定說明）；MongoDB 紀錄 metadata.retrieval.low_confidence 為 true。答案若被輸出防護攔截，則沿用既有的防護行為，不適用前述的歷史與回應來源規則。
- 高信心回應：confidence_note 為空字串；答案沒有固定說明；來源與快取行為與現在相同。
- 輸出防護攔截時（包含低信心的答案）：沿用既有行為（回傳安全訊息、回應來源為 guardrail、不寫歷史與快取），僅在 metadata 多帶 retrieval 物件。

**Interface / data shape**

- src/retrieval_grader.py 新增取得 top-1 分數的函式：輸入為 rerank_scores 清單，回傳浮點數；清單為空回傳 None；依 rank 最小者取分。grade_documents 與 rewrite_for_retry 的簽章不變。
- src/rag_pipeline.py 新增常數 LOW_CONFIDENCE_PREFIX 與 LOW_CONFIDENCE_NOTE；生成鏈接受選用輸入鍵 confidence_note，缺省為空字串。
- LOW_CONFIDENCE_PREFIX 參考文字：「知識庫中查無與此問題直接相關的資料，以下為一般性參考說明，實際操作請以官方操作手冊或系統畫面為準。」
- LOW_CONFIDENCE_NOTE 參考文字：「檢索到的資料與問題的相關性低。只有在資料中明確寫出能回答問題的內容時才可引用。若問題是關於 CarbonM 產品本身（功能、介面、版本、價格、是否支援某項目等）而資料中沒有寫，請明確說明無法確認，不要推測，也不要斷言有或沒有；只有一般常識性的問題才可以用一般知識簡短回答。不得杜撰 CarbonM 系統的具體操作步驟、畫面或選單名稱；不需要重複說明知識庫查無資料，系統會自行加註。」
- MongoDB metadata：metadata.retrieval 物件，欄位如上；其餘欄位不變。
- 事件格式、前端、公開 API 不變。

**Failure modes**

- rewrite_for_retry 出錯：回傳原查詢，依「與已試過的查詢相同則停止」處理，不產生錯誤。
- 取得 top-1 分數遇到格式異常的項目：沿用 grade_documents 的處理方式（以 rank 與 score 欄位為準），不新增吞錯的分支。
- metadata 寫入失敗：沿用既有 MongoDB 寫入的錯誤處理。
- 模型輸出違反低信心說明（例如仍杜撰步驟）：標示仍然存在；內容是否杜撰無法由程式保證，列為風險。

**Acceptance criteria**

- tests/test_chat_service.py 驗證：重試較差時保留原結果、較佳時採用重試結果、同分保留原結果；改寫相同或為空時檢索只發生 1 次且 retry_count 為 0；RETRIEVAL_MAX_RETRIES 為 2 時的停止條件；低信心時生成輸入帶非空 confidence_note、答案開頭為固定說明、事件序列無 sources、快取沒有寫入、歷史有寫入且含固定說明、metadata.retrieval 的各欄位（含 threshold 與 retry_skipped）正確；低信心的答案被輸出防護攔截時沿用既有行為（防護訊息、回應來源 guardrail、不寫歷史與快取）；高信心時 confidence_note 為空、答案無固定說明、來源與快取照舊；沒有檢索結果時視為低信心。門檻相關案例固定門檻值。
- tests/test_retrieval_grader.py 驗證取得 top-1 分數函式（正常、空清單、順序無關），以及 grade_documents 與它在門檻邊界一致。
- tests/test_rag_prompt.py 驗證提示詞渲染：未提供 confidence_note 時可正常渲染、內容不含說明，且渲染結果與修改前逐字相同（不多出換行，以免影響評估基準）；提供時說明出現在 system 訊息中；LOW_CONFIDENCE_PREFIX 與 LOW_CONFIDENCE_NOTE 均不觸發既有的 injection 與 PII 偵測。
- 人工驗證（需要金鑰、會產生費用，由使用者執行）：3 個知識庫外的問題與 3 個知識庫內的問題，確認低信心標示、無來源、快取不新增、MongoDB 紀錄欄位。
- architecture.md 與 README.md 已更新。

**Scope boundaries**

- 範圍內：src/chat_service.py、src/retrieval_grader.py、src/rag_pipeline.py、對應測試、architecture.md 與 README.md 的功能條目。
- 範圍外：src/cache_service.py、事件格式與前端、門檻與重試上限預設值、評估腳本與題庫、拒答模式、scripts/real_rag_smoke.py。

## Risks / Trade-offs

- [模型仍可能杜撰操作步驟，說明只能降低機率] → 標示由伺服器保證存在；杜撰比例需靠評估題庫量測，但評估腳本目前繞過評分與重試，需另案修改後才能量測。
- [門檻 0.3 未經驗證，可能把實際可用的結果標為低信心] → 仍保留 context 讓模型參考；新增的檢索紀錄可用來日後調整門檻。
- [被關鍵字誤路由的一般問題也會加上「查無直接相關資料」的說明] → 已接受；說明措辭中性，後續回答仍然提供。
- [低信心答案永不快取，重複出現的知識庫外問題每次都付完整的檢索與生成成本；fix-cache-lookup-coverage 讓高信心命中更穩定後，這個差距會更明顯] → 已接受，這是為了避免固化低品質答案；若成本成為問題，可另案針對重複出現的知識庫外問題做專門處理。
- [固定說明存入對話歷史，會被帶進後續的 prompt（生成的歷史區塊與追問改寫），可能使模型在之後的回答模仿這句開頭，或影響路由判斷（推測，無實測）] → 歷史維持存全文，使重新整理頁面後仍看得到標示（前端讀取的是同一份歷史），不改為只存模型生成的部分；若觀察到問題，再於組 prompt 時去除開頭的固定說明（需同時修改生成與路由兩處，另案）。
- [低信心時隱藏來源，若答案其實用到了 context 會減少透明度] → 偏向保守；若日後有資料顯示誤判率高再調整。
- [部署前已存在的低品質快取答案仍會留到 24 小時 TTL 結束] → 若與 fix-cache-lookup-coverage 同版部署，新索引使快取冷啟動可順帶清掉；否則由維運者手動清除快取。
- [新增 prompt 變數可能影響其他呼叫端] → 預設值為空字串且鎖定版本的合併規則已確認；以測試固定。
- [模型照抄說明時，輸出可能被既有輸出防護的寬鬆規則誤擋] → 說明文字避免相關詞彙；防護規則本身的問題另案處理。

## Migration Plan

1. 合併後部署，不需要資料遷移，也沒有新設定。
2. 建議先於 fix-cache-lookup-coverage 合併，或兩者同版部署；若反過來，兩次部署之間寫入的低信心答案會在快取範圍擴大後被穩定命中。單獨部署且需要立即清除既有的低品質快取時，需由維運者直接在 Redis 刪除快取 key（目前沒有端點或呼叫端能觸發 clear_cache）。
3. 回復：回到舊版程式碼即可；已寫入的 metadata.retrieval 欄位對舊版無影響。

## Open Questions

- 低信心時是否改為直接拒答（產品決策）；本變更預設為標示後回答，若改為拒答，需調整流程與測試。
- 是否在介面顯示低信心標記（需要新增事件欄位與前端驗證，另案）。
- 門檻 0.3 的合理性，待累積檢索紀錄與標註題庫後再評估。
- 評估腳本如何納入評分與重試路徑（另案）。
- 是否在組 prompt 時去除歷史中的固定說明（觀察到模仿或路由偏移時再決定）。
