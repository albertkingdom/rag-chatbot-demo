## Context

`src/query_router.py` 先以 `_rule_route` 比對 `RAG_KEYWORDS`（子字串、不分大小寫）與 `DIRECT_PATTERNS`，判不出來才呼叫 `_llm_route`（Gemini 2.5 Flash，temperature 0，structured output）。以 2026-10-21 的實測：範例手冊 60 題中規則層判定 40 題，其餘 20 題經 LLM 路由，「如何修改個人資料？」「如何開啟兩步驟驗證？」穩定判為 `direct`。RAG 關鍵字優先於 direct 規則；判為 `rag` 但檢索分數不足時，低信心機制會在回答前加上固定說明。已知問題中，「忘記 Gmail 密碼」因含「密碼」被判為 `rag`，又因檢索分數高，以 CarbonM 的重設流程回答。

## Goals / Non-Goals

**Goals:**

- 範例手冊全部問題實際路由為 `rag`。
- 規則層直接判定至少 42/60，不新增一般問題的誤判。
- 評估流程能抓到路由退化。

**Non-Goals:**

- 不改兩階段架構、RouterResult、改寫與低信心機制。
- 不處理「忘記 Gmail 密碼」這類既有關鍵字造成的誤判。

## Decisions

### 只加 CarbonM 專屬的複合詞

`_rule_route` 以子字串比對且 RAG 關鍵字優先於 direct 規則，單字詞容易撞到一般問題（例如「係數」會命中「相關係數是什麼？」，「盤查」會命中「倉庫庫存盤查」，「範疇」會命中「哲學的研究範疇」）。因此只新增在 CarbonM 情境外幾乎不會出現的複合詞：盤查年度、盤查報告、範疇二、範疇三、第三方查證、係數庫。「廠區」「佐證文件」「批次匯入」「啟用信」「範疇一」也會撞到一般問題（例如「工廠廠區的消防規定」「論文的佐證文件」「Excel 如何批次匯入資料」「Google 帳戶沒有收到啟用信」「研究範疇一般如何劃分」）；「數據填報」「填報截止」「填報人員」會撞到 Excel、Google 表單的問題，也不加入。實測規則層判定手冊 42 題，其餘 18 題交由 LLM 路由，評估腳本的關卡確認全部為 `rag`，下列反例皆不被規則層判為 `rag`：什麼是機器學習？、推薦一本好看的小說、明天要不要帶傘？、幫我想一個生日派對的主題、遊戲角色怎麼練等、台灣的首都是哪裡？、怎麼學好英文？、如何修改 Gmail 的個人資料？、Excel 報表怎麼做樞紐分析？、iPhone 如何開啟兩步驟驗證？、數據分析要學什麼？、相關係數是什麼？、如何查證網路謠言？、哲學的研究範疇有哪些？、幫我寫 Python 計算相關係數、Excel 如何匯入數據？、倉庫庫存盤查要注意什麼？、GDP 的基準年是什麼意思？、如何煮咖啡？、原始數據要怎麼清理？、Excel 如何批次匯入資料？、Google 帳戶沒有收到啟用信怎麼辦？、哲學的研究範疇一般如何劃分？、兩步驟驗證和雙因素驗證有什麼差別？、工廠廠區的消防規定有哪些？、論文的佐證文件要怎麼準備？、如何在 Excel 製作數據填報表？、Google 表單可以設定填報截止時間嗎？、Google 表單的填報人員怎麼設定？

「報表」「兩步驟驗證」「個人資料」「數據」「角色」「基準年」同樣不加入：在一般對話常見，誤判為 `rag` 時檢索可能找到 CarbonM 的高分條目，低信心機制攔不下。這些交由 LLM 路由。

### LLM 路由 prompt 列出系統功能並限定條件

prompt 列出 CarbonM 知識庫的功能類別：帳號與安全（登入、密碼、個人資料、兩步驟驗證、帳號啟用與停用）、角色與權限、廠區與盤查邊界、排放源與排放係數、數據填報匯入與審核、報表清冊與儀表板、第三方查證。判斷規則：

- 碳盤查、排放與溫室氣體相關的概念或做法判為 `rag`（例如「什麼是基準年？」）。
- 在系統中如何操作、設定或系統會怎麼處理的問題，屬於上述功能類別且沒有指明其他產品或服務時判為 `rag`（例如「如何修改個人資料？」「如何新增廠區？」）。
- 指明其他產品（例如 Gmail、iPhone、Excel）、一般資訊或資安概念（例如「兩步驟驗證和雙因素驗證有什麼差別？」）、與功能類別無關的一般操作（例如煮咖啡）、常識、閒聊判為 `direct`。

誤判為 `rag` 的代價：每次多做 embedding、檢索、重排，低分時還會改寫重試，最後才加低信心說明；若檢索剛好高分，會以 CarbonM 的內容回答並寫入快取。因此 `rag` 限定為碳盤查概念，或「在系統中的操作」且未指明其他產品；一般 IT／資安概念即使屬於帳號安全類別也判為 `direct`。

### 評估腳本的路由關卡

`scripts/eval_sample_manual.py` 在同步檢查之後、RAGAS 之前執行：

1. 以 `route_query(question)`（無歷史）路由範例手冊全部問題與評估集全部問題，必須為 `rag`。
2. 路由上述 29 個一般問題反例中規則層判為 `uncertain` 的部分，必須為 `direct`。
3. `RouterResult.reasoning` 以「LLM 路由發生錯誤」開頭代表 LLM 呼叫失敗（`_llm_route` 的錯誤回退），該題重試一次；仍失敗則列為「路由服務錯誤」，與誤判分開列出。
4. 有任何誤判或服務錯誤即中止，並列出題目、結果與 reasoning；同時印出規則層直接判定的題數。

實際 LLM 呼叫次數約 20 次（只有規則層判不出來的題目會呼叫）。

## Risks / Trade-offs

- [LLM 判斷仍有隨機性] → temperature 0；評估腳本每次執行都檢查正反兩組問題，實作驗收要求連續兩次完整通過。
- [prompt 規則讓少數邊界問題走 `rag`] → `rag` 條件要求同時屬於功能類別，反例關卡會抓到明顯的退化。
- [新增關鍵字可能讓含這些詞的一般問題走 `rag`] → 這些詞都是盤查或 CarbonM 專屬用語；反例測試涵蓋常見情境。
